# Память чат-бота: решение

## Зачем не хватает одного localStorage

По ТЗ память нужна одновременно для:

1. **Гостя** (не залогинен) — несколько дней, в т.ч. welcome «Есть проблемы с авторизацией?»
2. **Авторизованного пользователя** — история бота + обращения в поддержку
3. **Поддержки** — чужие чаты, неотвеченные, закрытие тикетов, welcome по статусу очереди

Поддержка и пользователь должны видеть **одни и те же** сообщения. Это невозможно надёжно сделать только в браузере пользователя.

## Выбранный подход: гибрид (visitorId + сервер)

```
┌─────────────┐     visitorId / login      ┌──────────────────┐
│  React UI   │ ─────────────────────────► │  API + БД        │
│  (виджет)   │ ◄── messages, tickets ──── │  (источник правды)│
└─────────────┘                            └──────────────────┘
       │
       └── local: UI-шаг меню, draft, кэш, TTL гостя
```

### 1. Идентичность

| Кто | Ключ | Где живёт |
|-----|------|-----------|
| Гость | `visitorId` (UUID) | `localStorage` + cookie, TTL **7–14 дней** |
| Пользователь | `login` (+ привязка `visitorId`) | сервер после авторизации |
| Поддержка | `login` + роль `support` | сервер (список ролей) |

При логине: **merge** гостевой истории `visitorId` → аккаунт `login` (не терять диалоги до авторизации).

### 2. Что где хранить

| Данные | Хранение | Почему |
|--------|----------|--------|
| Текущий шаг меню бота, черновик ввода | React state + `sessionStorage` | эфемерно, только UI |
| Прогресс сценария бота у гостя | `localStorage` / IndexedDB + синк на сервер | переживает перезагрузку на несколько дней |
| Тикеты поддержки, все сообщения user/support/bot в тикете | **только сервер** | нужна сторона поддержки и единая история |
| Закрытые обращения (read-only история) | сервер | опции 1.1.3 / 2.1.3 |
| Контекст `{fullname, firstname, login, dsNumber}` | пропсы/API с хоста + сервер | не «память чата», а контекст сессии |
| Welcome msg + waitingTime | **вычисляются** из состояния на клиенте или API | правила из ТЗ, не отдельное хранилище |

### 3. Минимальная модель БД

- `visitors` — `id`, `expiresAt`, `linkedUserId?`
- `users` — `login`, `fullname`, `firstname`, `role: user | support`
- `conversations` — `id`, `visitorId?`, `userId?`, `kind: bot | support`, `status: open | closed`, `dsNumber?`, `dsName?`, `createdAt`, `lastMessageAt`
- `messages` — `conversationId`, `sender: bot | user | support`, `text`, `createdAt`

Индексы: открытые support-чаты по `lastMessageAt`; непрочитанные = open + last sender = user (для поддержки).

### 4. Синхронизация и welcome

- Пока открыт виджет: **SSE или короткий polling** (5–15 с) для новых ответов поддержки.
- Welcome / waitingTime — чистая функция от снапшота:

  - гость → «Есть проблемы с авторизацией?»
  - есть ответ поддержки в текущем чате → «У вас есть ответы…», waiting = 5 с
  - поддержка: неотвеченные / активные / все решены — по правилам ТЗ

### 5. Почему не альтернативы

| Вариант | Вердикт |
|---------|---------|
| Только localStorage | Поддержка не видит чаты; сброс браузера = потеря |
| Только сервер без visitorId | Гость без login не получит память на дни |
| Firebase / Supabase realtime | Можно как реализацию сервера; модель та же |
| Typebot cloud memory | Не даст кастомную сторону поддержки и BI-контекст |

## Стек реализации (рекомендация)

- Frontend: React (виджет + отдельная страница поддержки)
- Backend: Node (Express/Fastify) или тот же стек, что у BI-сервиса
- БД: PostgreSQL (прод) / SQLite (локальная разработка)
- Realtime: SSE на старте; WebSocket позже при нагрузке

## Итог одной фразой

**Сервер — источник правды для диалогов и тикетов; в браузере — visitorId с TTL и кэш UI; при логине — слияние гостя с аккаунтом.**
